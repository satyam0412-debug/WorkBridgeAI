## Current architecture

The project started with an AIService that directly handled AI generation.

We refactored it toward a provider-independent architecture.

Current intended architecture:

Controller
↓
MessageService
↓
AIRouter
↓
MessageGeneratorFactory
↓
MessageGenerator interface
├── GeminiMessageGenerator
├── OpenAIMessageGenerator
└── future providers

Each concrete generator owns its own ChatClient and knows how to communicate with that AI provider.

AIRouter decides which provider should handle the request.

MessageGeneratorFactory returns the appropriate MessageGenerator.

MessageService should NOT know about individual AI providers.

## MessageGenerator

Interface:

MessageGenerator

Its implementation classes include:

* GeminiMessageGenerator
* OpenAIMessageGenerator

The generator method currently returns:

GeneratedMessage

rather than String.

Reason:
GeneratedMessage can carry the generated text plus provider metadata and can later contain model, token usage, cost, latency, request ID, etc.

## GeneratedMessage

Current concept:

* formattedMessage
* provider / culturalInsight depending on current DTO implementation

The API response has looked like:

{
"success": true,
"message": "Message generated successfully.",
"data": {
"formattedMessage": "...",
"culturalInsight": "Generated by OpenAI 🤖"
}
}

## MessageGeneratorFactory

Current responsibility:

* Return the correct MessageGenerator for a provider.
* It should NOT contain ChatClient logic.
* It should NOT generate AI responses.
* It should not directly know prompt logic.

Previously it looked approximately like:

@Component
public class MessageGeneratorFactory {

```
private final GeminiMessageGenerator geminiGenerator;

public MessageGeneratorFactory(GeminiMessageGenerator geminiGenerator) {
    this.geminiGenerator = geminiGenerator;
}

public MessageGenerator getGenerator(String provider) {

    if ("gemini".equalsIgnoreCase(provider)) {
        return geminiGenerator;
    }

    throw new IllegalArgumentException(
        "Unsupported AI provider: " + provider
    );
}
```

}

We later added OpenAI support.

A Map-based Factory was discussed as the preferred long-term approach because more AI providers will eventually be added.

## AIRouter

New package:

backend/src/main/java/com/workbridge/backend/router/

New class:

AIRouter.java

Purpose:

* Decide which provider should generate the response.
* Support explicit provider selection.
* Support automatic fallback.
* It must NOT contain ChatClient code.
* It must NOT depend directly on GeminiMessageGenerator/OpenAIMessageGenerator.
* It depends on MessageGeneratorFactory.

Current conceptual flow:

provider = gemini
→ Factory → GeminiMessageGenerator

provider = openai
→ Factory → OpenAIMessageGenerator

provider = auto
→ try Gemini
→ if Gemini fails
→ try OpenAI

AIRouter should return GeneratedMessage.

## GeminiMessageGenerator

Current important behavior:

GeminiMessageGenerator implements MessageGenerator.

It owns:

private final ChatClient chatClient;
private final PromptLoader promptLoader;

Constructor:

public GeminiMessageGenerator(
ChatClient.Builder builder,
PromptLoader promptLoader) {
this.chatClient = builder.build();
this.promptLoader = promptLoader;
}

It loads the scenario prompt using:

ScenarioFileMapper.getFileName(scenario)

and:

promptLoader.loadPrompt(fileName)

It loads the base prompt using:

promptLoader.loadBasePrompt()

and replaces:

{{scenarioInstruction}}
{{relationship}}
{{message}}

Then calls:

chatClient.prompt(prompt)
.call()
.content();

IMPORTANT:
GeminiMessageGenerator used to swallow exceptions and return:

"Sorry, the AI service is currently unavailable. Please try again later."

That prevented AIRouter fallback.

We changed it so that the exception is rethrown:

catch (Exception e) {
logger.error("Failed to generate business message.", e);
throw new RuntimeException(
"Failed to generate business message.", e
);
}

This allows AIRouter to detect provider failure and fall back to OpenAI.

## MessageService

MessageService should NOT directly select Gemini/OpenAI.

## Prompt system

We created:

PromptLoader.java

and:

ScenarioFileMapper.java

ScenarioFileMapper currently maps scenario names to prompt filenames.

Example:

public static String getFileName(String scenario) {
return scenario
.toLowerCase()
.replace(" ", "-")
+ ".txt";
}

A fallback such as:

return "default.txt";

was also discussed.

Prompt files are currently under:

backend/src/main/resources/prompts/

The longer-term idea is to move scenario prompts from .txt files into the database.

If prompts move into the database:

* ScenarioFileMapper should eventually stop mapping to physical files.
* PromptLoader should retrieve prompts from DB.
* AI generators should continue asking PromptLoader for prompts rather than directly accessing DB.
* This keeps AI generators clean.

   "gemini"
   "openai"
   "auto"

with an enum such as:

AIProvider {

   ProviderUnavailableException
